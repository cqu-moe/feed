# MVP 存档迁移

正式版使用新增的版本表和不可变对象保存 MVP 基线。原 `articles`、`attachments` 中的正文与文件引用，以及旧 R2 对象继续保留；不删除原件，不在迁移时访问源站或重新付费 OCR。

## 执行范围

先在隔离 D1/R2 副本应用全部迁移，再进行有界导入。迁移入口沿用现有管理员鉴权；`POST /internal/archive-migration` 接收 `requestId` 与 `batchSize`，`GET /internal/archive-migration` 返回持久进度和比对报告。重复操作使用原 `requestId`。

每篇旧存档只建立一个 `migrated` 基线。文件字节、hash、正文 PDF 页数及 OCR 输入身份不能确认时，正式版本保持缺项状态，不能因为旧记录标为 `complete` 就发布。迁移事件只具备历史资格，供网页与 RSS 展示，不建立历史邮件洪峰。

管理员先提交带固定 `requestId` 的迁移请求；批次完成后读取状态。仍有未处理项时，调用 `POST /internal/archive-migration/process` 继续，每次只处理配置的有界数量。进度落在 D1，客户端退出后可继续，不依赖本机进程保持连接。相同请求重放不会另建迁移基线，不同请求身份不能覆盖正在进行的迁移。

缺项修复使用 `POST /internal/archive-migration/repair`，正文为 `{"articleId":"原通知 ID"}`。它只补未完成的必要项；已确认的文件与历史原件保持不变。缺失原件必须有迁移时已保存的预期 hash 才能确认属于同一版本；不能把后来出现的新文件拼入旧版本。无法确认旧字节身份时继续保留差异，另行采集形成新版本。

旧 OCR 结果要与正文 PDF 的原始字节、模型记录和所有页对应。某页已有可读文本并不证明其余页面完成；缺少扫描页结果时仍保持缺项。修复 OCR 只采用对应原 PDF 的结果，不重新下载已保存原件，也不在此入口隐式发起付费识别。

## 比对与切读

核对旧通知、附件、来源关系、已完成 OCR 与新版本的数量；逐项检查原件 hash、OCR 输入和页数。不能确认的差异保留在报告中。管理员应通过阅读入口验证中文搜索、正文、历史版本、快照、PDF Range 和权限。

聚合进度从 `GET /internal/archive-migration` 读取。逐篇证据从 `GET /internal/archive-migration/articles?limit=20` 读取，下一页带返回的 `nextCursor` 作为 `after`。每页最多 100 篇，包含初次冻结的附件 hash/尺寸、OCR 任务身份和预期数量，以及当前实际原件 hash、OCR 输入与输出身份、来源日期证据和差异；不要只用总数相等代替逐项核对。来源日期继续保留日级或分钟级精度，未知日期保持未知。

`ARCHIVE_READS_ENABLED=true` 使用正式版阅读投影；`false` 恢复 MVP 阅读。切换只改变读取路径，新旧已保存资料都保留。回滚后要再次检查旧链接、搜索与已登录会话；不要把 Worker 代码回滚误认为数据库或 R2 回滚。

## 验收状态

本地 Worker/Miniflare 验收已覆盖完整导入及切读回滚、缺失或失败 OCR 恢复、原件 hash 冻结、多页 OCR 与输入身份、分批及并发继续、R2 成功后 D1 中断恢复、部分修复报告，以及修复后相同源内容复查不生成实质修改。修复成功仍保留原采集时间无法确认等历史差异，重复修复不重复记录相同证据。与 RSS 集成后的全量 86 项测试、构建、设计检查和 Worker dry-run 已通过，独立审查通过。
