# 采集调度

每个栏目各算到期：成功查过列表（包括有效空列表）后，下次检查时间是这次成功时间加栏目的刷新间隔，默认一天。每小时整点，Cron 找出站点和栏目都启用、配置已验证、已到期且没有在办列表任务的栏目。每栏各建一项首页任务；同一站点在这一轮共用一个最早开工时刻。它由站点 ID 和 Cron 原定的 UTC 整点确定，位于这一小时内；Cron 重入或分批扫描不会再抽一次。

任务的 `due_at` 是最早开工时间。消息立即发送，由 **Queue 的单条消息延迟**等待。发送失败后补发，只设置剩余时间；已正常发送且仍在等待的消息不能被后台再次补发。等待时不启动 Workflow 或容器。手动验证、翻页、正文、版本复查和历史补抓不加这份随机等待。界面和监控只给已正确安排的本轮检查保留处理宽限；上轮漏查、出错或根本没安排都应可见。

**Workflow 执行方式：**Queue 收到启动消息后，以任务 ID 和本次尝试生成固定的 Workflow 身份，确认接手后才确认消息。Workflow 开浏览器前核对有效性、取得本站执行权；定时列表发布结果前再核对。不同网站可以同时抓取；同站同一时刻只用一个浏览器。永久错误、额度耗尽、可重试的源站故障和平台暂无容器要分别处理。源站限流或临时故障时释放浏览器，在原 Workflow 中等待并有限重试；站点忙和平台等待不消耗源站抓取次数。

列表检查产生来源关联、首次正文任务及必要的续页；同一通知出现在两个栏目只建一次首次正文任务。正文交回原件后即可释放本站执行权，归档写入与独立 OCR 不占用浏览器。只有内容和必需附件等齐备的版本会发布内容事件。历史补抓暂停时保留当前游标，须由管理员恢复。五分钟 Cron 仍负责失联交接、监控及原有邮件等维护，不推进一个健康 Workflow 的正常重试。

**切换执行器时：**

1. 暂停目标采集 Queue 的投递（`wrangler queues pause-delivery <采集队列>`）。继续保留任务、启动消息和新进入的积压。邮件、OCR 和内容事件不参与这次交接。
2. 按任务 ID、尝试号和 `task_attempts.workflow_instance_id` 列出仍在执行的旧尝试。旧消费者的身份以 `queue-` 开头。核对 D1 业务结果、列表或正文原件；结果不明时保持暂停，不能仅凭队列为空或消息已确认就当作采集成功。
3. 旧执行退出或结果核清后，在目标环境把 `COLLECTION_EXECUTOR` 改为 `workflow` 并部署。保持原队列、数据库、存储桶和 Workflow binding。用 `wrangler queues resume-delivery <采集队列>` 恢复投递，核对未领取的旧任务沿用原 ID，新的尝试由相应的 Workflow 接手。
4. 如需退回 `queue`，同样先停领，等已由 Workflow 接手的尝试结束并核实其记录，再恢复投递。切换前后不重置历史失败、已阻塞或已成功的任务，不回滚已发布的通知版本或事件。
