# 采集调度

Cron 每小时按原定 UTC 整点扫描启用、验证通过且到期的栏目。用站点 ID 和该整点生成 0～3599 秒偏移，将最早开工时间写入现有 `tasks.due_at`；outbox 立即可派发，统一发送入口把剩余秒数向上取整交给 Queue 的 `delaySeconds`。等待期间不创建 Workflow、不访问源站。同一栏目有 queued、starting、running 或 deferred 列表任务时不创建新一轮；并发 Cron 通过下一次到期时间的条件更新与任务业务键去重。

只有整点的首轮列表任务错峰；显式管理员调度、样本验证、后续翻页、新正文、复查、历史补抓和重试不额外错峰。派发积压、历史页和五分钟恢复不会扫描到期栏目。

成功检查后，下次检查为成功时间加刷新间隔，默认一天。有效空列表或没有新通知也会更新成功时间。入队时暂将下一轮设为当前时间加间隔，失败由当前任务的有限重试处理，不能因成功时间未更新而每小时新建任务绕过重试上限。

`feed-jobs` 每批一条消息，最大两个消费者。新列表、正文、复查和历史页任务在消费者内完成采集并保存结果，然后确认消息，因此该限制覆盖实际采集。同一站点继续共用一个容器和已有站点执行租约；忙碌任务延期，不在容器内等待。已有 Workflow 尝试保留恢复路径，OCR 继续使用原有 Workflow。

Queue 消费有 15 分钟平台时限。分页各自入队；超时或消费者丢失后的恢复沿用任务尝试次数、保存的结果和退避，不能假记成功。不得将超过该时限的整站抓取合并成一条消息。

迁移 `0021` 将没有在途列表任务的启用栏目的下一次时间恢复为最近成功时间加间隔。它不修改成功时间、不清空失败记录，也不启动历史补抓。`0020` 的全天站点错峰不再是当前调度规则。

PostHog 每五分钟记录任务尝试结果、积压与来源新鲜度。来源超期同时检查实际成功时间和遗漏的计划时间。没有有效排班时沿用一个小时调度窗口加十分钟处理时间；本轮有效排班改按最早开工时间加十分钟判断，页面显示等待、处理中或超期，不刷新成功时间。首次计划同时保存在任务 payload 的 `scheduledStartAt`，来源状态始终使用该值，Workflow 改写 `due_at` 的重试/退避不会重新获得宽限。有效排班来自当前已验证配置的首轮在办任务及无发送错误的启动 outbox；到期时间必须属于本轮前一小时，旧漏检、错误、配置变更、停用或重试不会被新排班掩盖。邮件和失败恢复仍每五分钟执行；没有当前报错不能作为恢复证明。生产验收须检查所有启用栏目的实际成功时间以及新任务结果。
