本次新增栏目按用户选择每周检查一次（604800 秒），原有来源保持既有刷新间隔。按每次最多两页估算，51 个新栏目的列表检查约需 437 credits/30 天；正文、样本验证和重试另计。新栏目从接入日开始发现更新，不自动回填历史。

## 2026-11-02 故障证据

生产 D1 只读检查显示：`civil`、`intex`、`news`、`xgb` 的 `enabled=0`、`next_discovery_at=0`，最近运行时间均为 2026-10-13；只有 `jwc` 启用，最近运行时间为 2026-11-02。数据库不能说明当初是谁、因何暂停。原界面只检查 `error` 和旧 `last_run_at`，因此把没有错误的暂停来源显示成“运行正常”。

学工部旧错误是停用前留下的 `No article links found in list`。本次实时重放发现首页十条通知中，原规则只能识别九条：一条使用 `detail.jsp?urltype=news.NewsContentUrl&wbtreeid=1024&wbnewsid=5808`。该动态页面返回“系统提示”，同文的 `/info/1024/5808.htm` 正常返回正文及附件入口。适配器将已确认的两种 CMS 动态文章模板规范到静态文章地址，保留同源和数字 ID 检查，避免漏采及别名重复。

发现任务的失败现同步到来源错误字段；空列表不会再更新成功时间。旧配置或早于更新成功结果的任务失败不能覆盖当前来源状态。历史补抓仅更新自身进度，不能清除日常检查错误或刷新其成功时间。来源页展示实际启用状态、刷新间隔和下次检查时间；长时间未成功检查会显示超期。

五个站点的首次生产样本验证均遇到 `Sample article body was not recognized`：配置的历史附件样本不在列表第一页，旧代码给它添加虚构标题“通知样本”，随后要求原文标题包含该字符串。修复后，不知道标题的样本必须出现明确的正文容器；已知标题仍执行标题匹配。浏览器回归直接运行验证流程，确认历史样本的正文、附件字节与原貌可以通过，同时拒绝无正文容器的访问挑战页面。同源、文章 URL、附件类型与哈希校验保持有效。

正文修复上线后，学工部样本继续在附件下载环节失败。实测附件返回验证码页面，`feed.cqu.moe/internal/bridge` 对脚本请求返回 Cloudflare 挑战，而既有 workers.dev 同路径返回应用的临时授权校验。采集与样本验证的辅助窗口改用显式 `BRIDGE_BASE_URL`；浏览器回归模拟业务域名被挑战，实际打开辅助窗口并完成验证码响应和附件下载。该设置不改变 OAuth 回调，也不修改站点 WAF；桥接继续使用来源绑定、五分钟 HMAC capability、窗口与消息来源校验。

本地验证包含真实列表 HTML 重放、真实 Worker/D1 任务测试和浏览器界面回归。它们不替代生产启用、真实账号登录或完整附件存档验收；具体部署与接入结果在交付时另行记录。

## 生产验证补充

2026-11-02，PR #43、#44 已通过 PR 和 main 的七项检查，并由 Git Connector 发布。土木学院、国际处、新闻网恢复后已观察到新成功采集时间；学工部使用 `/info/1024/5803.htm` 的公开 PDF 完成正文、原文件和快照验证后恢复启用。该 PDF 的源站响应为 `application/pdf`，文件签名为 `%PDF-1.4`。

学工部 `/info/1024/5808.htm` 的两个验证码下载附件仍有失败：曾返回 `CAPTCHA attempt limit reached` 和 `No file or CAPTCHA (HTTP 200)`。更换验证样本不代表这两个附件已修复，后续遇到仍按现有失败/部分存档语义记录。没有放宽附件签名、同源或验证码检查。

接入时也出现管理 API 查询连接被重置（`UND_ERR_SOCKET`、`ECONNRESET`）。CLI 对 GET 连接失败最多尝试三次；写请求响应丢失后会报告失败，重新执行时先读取服务器现状。所有五个新站点的代表栏目均已通过生产样本验证，批量接入结果以管理 API 当前状态为准。

首次启用同时触发列表检查、正文采集和已有文章复查，实际触发了 Firecrawl 每分钟限流。生产使用已有 `MAX_LIVE_DISCOVERY_TASKS_PER_RUN=2` 配置，将每个一分钟准入窗口内的新列表任务限制为两个，为正文任务留出余量。该限制不改变每周刷新间隔；Cron 和完成任务后的派发负责继续处理队列。正文任务仍可能单独限流并进入原有延期重试。
