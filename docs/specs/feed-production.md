# CQU Feed 正式版 v1 规格

日期：2026-10-12（北京时间）。本规格定义目标行为与验收，不表示功能已实现或生产已验证。

## Problem Statement

现有 MVP 已能采集和阅读少量公开通知，但来源增加后，读者还需要按自己的栏目范围持续接收完整通知、查看原文修改前后的内容，并确信不会漏掉重要更新或收到重复邮件。管理员需要接入多个来源、补抓历史和恢复失败任务，不能靠重跑整站处理一个附件或 OCR 的故障。

目前的来源级串行采集、可被更新的单份文章记录和缺少个人投递账本的模型，尚不能完整承担这些要求。Auth 已有 Feed 访问权益，但尚无明确的订阅数量和后台已验证邮箱契约。

## Solution

建设一套共享采集、不可变版本存档、个人多订阅、一订阅一私有 RSS 的正式版。每篇通知独立完成正文、必要原貌、附件和正文 OCR 后才成为可推送通知；一篇失败不阻塞其他完整通知。邮件提供及时提醒与北京时间每日 20:00 摘要，默认摘要，并在用户层面对同一内容事件去重。

抓取使用 Cloudflare Queues 与 Workflows，原件保存到私有 R2，关系、任务、内容事件和投递事实保存到 D1。Auth 管理访问能力及订阅配额，Feed 执行配额并保留降额后的配置。管理员能够看见缺项、延期和结果不明等不同状态，针对具体任务恢复。

## User Stories

1. 作为读者，我希望从一个入口查看多个部门和学院的公开通知，以便不必逐站刷新。
2. 作为读者，我希望按标题、正文和来源搜索已存档通知，以便找到所需信息。
3. 作为读者，我希望查看通知原貌、正文 PDF 和附件，以便核对原始内容。
4. 作为读者，我希望正文型扫描 PDF 完成必要 OCR 后可以阅读和检索，以便理解通知正文。
5. 作为读者，我希望未完整的新版本不替换已有完整版本，以便继续可靠地阅读存档。
6. 作为读者，我希望查看每次实际捕获的原文和附件版本，以便追溯后来发生的修改。
7. 作为读者，我希望同名附件被替换后仍能下载旧版本，以便保留当时的材料依据。
8. 作为读者，我希望提醒链接指向当次版本，以便稍后阅读时知道提醒针对什么内容。
9. 作为用户，我希望创建多个独立订阅，以便分别管理不同关注范围。
10. 作为用户，我希望按站点或栏目选择订阅，以便关注相关通知。
11. 作为用户，我希望选择整个站点时只纳入当时已有栏目，以便订阅范围不会被悄悄扩大。
12. 作为用户，我希望编辑订阅栏目、名称和启停状态，以便调整自己的关注范围。
13. 作为用户，我希望后来加入的栏目从加入时开始计算邮件资格，以便不收到旧通知补发。
14. 作为用户，我希望每个订阅有一个独立私有 RSS，以便在阅读器中分别使用。
15. 作为用户，我希望独立撤销或轮换某个 RSS 链接，以便不影响其他订阅。
16. 作为 RSS 使用者，我希望读取订阅范围内完整且日期已核实的历史通知，以便补看往期信息。
17. 作为 RSS 使用者，我希望每次实质修改出现一个稳定的“更新”条目，以便阅读器识别新消息。
18. 作为 RSS 使用者，我希望重复刷新不会产生重复条目，以便维持清晰的阅读记录。
19. 作为用户，我希望知道私有 RSS 持有者能看标题和摘要，而正文与附件仍需登录，以便理解链接的访问范围。
20. 作为用户，我希望逐订阅选择不发邮件、及时提醒或每日摘要，以便控制打扰程度。
21. 作为新用户，我希望订阅默认使用每日摘要，以便集中接收通知。
22. 作为用户，我希望所有必要产物准备好后才收到提醒，以便点开就能阅读完整通知。
23. 作为用户，我希望同一通知命中多个订阅仍只提醒一次，以便避免重复邮件。
24. 作为用户，我希望每天北京时间 20:00 收到一封合并摘要，以便集中阅读不同订阅的内容。
25. 作为用户，我希望没有新内容时不发空摘要，以便减少无效邮件。
26. 作为用户，我希望已及时提醒过的同一内容事件不再进入摘要，以便避免二次打扰。
27. 作为用户，我希望稍晚完成归档或匹配的通知仍进入后续摘要，以便不因处理延迟漏报。
28. 作为用户，我希望只向 Auth 当前已验证邮箱发送邮件，以便地址和身份状态一致。
29. 作为用户，我希望邮箱未验证时保留订阅且 RSS 继续按自身权益工作，以便只暂停邮件。
30. 作为用户，我希望在 Feed 中看到 Auth 决定的订阅额度与运行状态，以便理解当前可用能力。
31. 作为用户，我希望降额时保留所有配置，只暂停超额订阅，以便以后恢复使用。
32. 作为用户，我希望选择额度内保留哪些订阅运行，以便优先关注重要来源。
33. 作为用户，我希望额度恢复后不自动打开自己主动关闭的订阅，以便保留个人意愿。
34. 作为用户，我希望 Auth 暂时故障时配置不被删除、权限不被误判为无限，以便故障可恢复。
35. 作为新订阅者，我希望历史通知可在网页和 RSS 查看但不补发邮件，以便避免收件箱被填满。
36. 作为新订阅者，我希望当天只有日级日期、且订阅后首次发现的通知也能提醒，以便尽量减少当天漏报。
37. 作为订阅者，我希望日期不明的通知先核实再推送，以便历史内容不被错误当成新消息。
38. 作为订阅者，我希望订阅前发布的旧文在订阅后发生实质修改时也收到更新提醒，以便及时发现新变化。
39. 作为订阅者，我希望仅排版变化或重新 OCR 不发更新提醒，以便消息聚焦原文实质变更。
40. 作为管理员，我希望维护站点、栏目及抓取配置，以便逐步接入更多公开来源。
41. 作为管理员，我希望先验证来源样本再启用定时抓取，以便及时发现分页、正文或附件适配问题。
42. 作为管理员，我希望重要栏目每 30–60 分钟检查、普通栏目每天数次，以便按需要分配刷新频率。
43. 作为管理员，我希望新来源默认补抓一年且可调整，以便建立可检索历史存档。
44. 作为管理员，我希望历史补抓不触发邮件洪峰，也不耗尽日常刷新预算，以便兼顾存档和及时性。
45. 作为管理员，我希望所有已存档通知按新旧分级复查，以便持续捕获后续修改。
46. 作为管理员，我希望看到每篇通知缺失的附件或 OCR 项，以便只修复失败部分。
47. 作为管理员，我希望限流、额度耗尽、解析失败和邮件结果不明分别显示，以便采用正确恢复方式。
48. 作为管理员，我希望重试同一任务不会重复存档、生成事件或发送邮件，以便安全恢复中断。
49. 作为运维人员，我希望数据库提交后即使暂未入队也能恢复执行，以便不丢工作。
50. 作为运维人员，我希望死信与已启动后失败的 Workflow 都能被发现，以便没有无人处理的任务。
51. 作为运维人员，我希望观察积压、归档延迟、付费调用、OCR 页数和投递状态，以便估算容量与预算。
52. 作为维护者，我希望把 MVP 数据导入为不会触发历史邮件的基线，以便保留现有存档和访问能力。
53. 作为维护者，我希望分开验证本地测试、云端交接、真实账号业务与上线回滚，以便明确交付证据。

## Implementation Decisions

1. 首版沿用一个 Feed Worker 部署与现有前端，Auth 独立；不引入自建微服务群、数据库分片、全局并发协调器或站点信号量。文章租约与 fencing token 只保护文章写入一致性。
2. 四个业务 Module 为 Sources、Archive、Subscriptions、Notifications，业务 Interface 隐藏流程顺序、存储和副作用细节。TaskRuntime 承担持久任务、实例身份、交接和恢复；平台与供应商通过实际需要的 Adapter 接入。
3. 三条业务 Queue 为任务启动、完整性/事件处理、邮件发送，各自配 DLQ；三个 Workflow 分别执行有限栏目发现、单篇采集和单输入 OCR。启动消息确认代表指定 Workflow 已接手，不代表归档或邮件已完成。
4. D1 保存站点/栏目、通知/来源关联、版本/必要产物、派生结果、用户关联、订阅/目标区间、内容事件/来源证据、匹配/投递、固定邮件、任务/attempt/outbox。每次业务状态推进与对应 outbox 在同一原子批中提交；受影响行数为零必须显式门控后续语句。
5. R2 保存不可变原件、版本清单、OCR 结果和邮件快照。对象按内容 hash 复用，版本引用不覆盖。D1 与 R2/Queue/外部供应商不存在跨服务事务；外部操作成功而本地记录未完成时，按持久身份恢复。
6. 同一 canonical URL 可关联多个栏目并共享通知版本；不同 URL 的转载不按标题或相似度自动合并。URL 规范化保留决定内容身份的参数。
7. 保留所有实际捕获版本，包括 A→B→A 的三次观测；只与紧邻观测相同才视为无变化。仅排版变化仍可留档，是否产生提醒另行判断。轮询不承诺恢复未观察到的中间版本。
8. 完整性按每版本冻结的必要产物清单判定。正文、必要原貌、附件和必要正文 OCR 全部成功后才能生成可推送事件；无需 OCR 的通知不创建无意义的必需项。旧完整版本持续可读。
9. OCR 是派生结果，以原件 hash、处理器版本与选项确定身份；重做 OCR 不覆盖原件或伪造源版本。旧 OCR 晚到不能回退最新完整阅读版本。补抓若发现源已变，创建新候选，不能混合新旧附件凑成完整旧版。
10. 内容事件一版本一个稳定身份；历史基线事件可供 RSS，但不会因此成为邮件候选。实质修改产生独立 update 事件，重复任务不重复产生事件。RSS GUID 与阅读链接均绑定该事件/版本。
11. 用户由 Auth 稳定 sub 关联，可有多个独立订阅。每个订阅保存明确栏目集合；选择整个站点只展开当时已有栏目，后来新增栏目不自动加入。目标移除再加入产生新的生效区间。
12. 订阅内嵌一份私有 RSS 凭证，保存高熵随机 token 的 hash 用于校验，并加密保存 token，供登录后的订阅所有者随时查看和复制当前链接。撤销/轮换、用户主动关闭、额度暂停是不同事实。私有 RSS 只输出标题、摘要和版本链接；原件、正文与快照继续要求登录及 feed.access。
13. 邮件资格与 ready 时间分开：准确发布日期不早于目标生效时间；日级日期不早于生效当地日期且该来源首次发现不早于生效时间；未知日期先核实。订阅前观察但之后才补齐的旧变化不补发。旧文在目标生效后新观察到的实质修改可发更新，不要求旧文原始发布日期晚于订阅。
14. 新来源历史导入默认一年，补抓/迁移只建历史基线，不制造新增或更新邮件。后来扩大订阅范围不追溯补发。来源关联与日期核实保留证据，不把第一次发现时间改成重试时间。
15. 邮件模式逐订阅配置，默认 daily_digest。按用户与内容事件设置唯一投递记录；及时与摘要共用占用。当前多个有效命中有及时模式时优先及时。固定消息收件人、内容和幂等键后提交；同一键不得改邮箱或追加内容。
16. 摘要北京时间每天 20:00 按用户合并，空集合不发送。以完整就绪时间纳入窗口，同时处理之前因匹配或故障滞留的合格 pending，避免仅按上次游标过滤造成丢失。已受理或提交结果不明的及时消息不能再次进入摘要。
17. Auth 保留 feed.access，新增 feed.sub_limit。新契约显式区分 limited、unlimited、missing；0 为零额度，missing 按未授予处理，脏值拒绝，网络失败不变成无限。现有 calendar/getCaps 及 Feed 网页访问契约保持兼容。
18. Auth 提供 Feed 专用 policy 与 recipient 两个 typed RPC，后者同次返回权限及当前已验证邮箱。Feed 业务调用者不接触凭证 envelope；独立服务身份、named binding、方法/子系统白名单与最少披露由 Adapter 承担。邮箱未验证只暂停邮件。
19. 创建数量统计所有未删除订阅配置；实际运行集合从用户希望启用的配置按优先级、创建时间、稳定 ID 取额度内部分。降额保留配置并允许重新排序，恢复后不覆盖主动关闭意愿。创建用稳定请求身份与条件写入；跨 Auth/Feed 无事务，写后降额返回“已创建但暂停”的明确事实。
20. RSS 读取和首次邮件提交前核实当前权益。明确暂停与 Auth 不可用分别处理，禁止缓存的旧许可绕过输出检查。RSS 权限检查先于条件读取/304；失效 token、明确暂停和暂不可用的状态可以区分。
21. 同源验证码与依赖该会话的文件抓取保持一个可重建采集单元。Workflow 只持久化步骤进度，不承诺保存远端浏览器会话。大对象只传 R2 引用，消息与步骤返回值保持小型。
22. 429 使用有界退避与抖动，402/余额或预算耗尽持久延期，不快速循环。Queue、Workflow、SDK 的重试职责不叠乘。服务商代理不会取消账户限流；不承诺付费调用在结果不明时绝对只计费一次。
23. 邮件区分待提交、受理、收件服务器接收、退信、投诉与 submission_unknown。结果不明时用原请求在供应商支持范围内对账；无法确认则保留占用并人工处理，不能盲目再发。Webhook 验签、持久去重后处理，乱序回调不能回退已确认事实。
24. 通道偏好、退信/投诉和权益暂停不删除归档。恢复积压重新评估资格，已有合格 pending 默认合并摘要，避免集中补发大量及时邮件。源站短暂不可达不被解释为删除，首版不发撤回邮件。
25. 管理员可以接入、验证、暂停来源，查看缺项、任务与预算原因，恢复具体 task/revision/message。管理员入口沿用独立鉴权，普通 feed.access 不授予管理权限，后台凭证不得硬编码或下发给普通浏览器用户。新任务意图与同任务重试使用不同身份规则。检查覆盖全部归档，分级频率配置化。
26. MVP 使用渐进迁移：新增模型、幂等导入、比对、切读与可回滚切换，旧原件/身份关系保留。旧 complete 不足以直接证明新版本 ready。搜索投影跟随最新完整版本，历史版本通过时间线读取。

## Testing Decisions

1. 主验收 Seam 沿用 Worker 已有用户/管理员 HTTP 入口：从请求或可控调度触发，观察存档阅读、订阅状态、RSS、邮件 Adapter 的接收记录和管理状态；不新增仅为测试存在的万能公开接口。
2. 无法通过 HTTP 精确覆盖的重放、时钟和故障窗口，通过 Sources、Archive、Subscriptions、Notifications 与 TaskRuntime 已定义的 Interface 验证。断言可观察行为与持久结果，不断言私有函数调用顺序或要求调用者自行准备租约。
3. 沿用当前测试先例：Miniflare 的 D1/R2、OAuth BFF 与实时权益、中文搜索/PDF Range/快照安全、OCR 缓存/预算/过期输入、Workflow 延期行为。原有独有安全证据保留；重复实现细节测试在 Interface 覆盖成熟后再替换。
4. Auth 使用生产 Service Binding Adapter 与测试内存 Adapter；Firecrawl、OCR、邮件使用生产 Adapter 与可控测试 Adapter。D1/R2 用真实本地语义验证条件写入和事务，不能让宽泛内存 repository 假装证明原子性。
5. 并发/重放验收覆盖相同请求只创建一次、同一事件多个订阅只占一个 delivery、版本就绪与 outbox 一起提交、队列确认后 Workflow 失败仍可恢复、实例创建后记账失败仍复用同一实例。
6. 时间验收使用受控时钟，覆盖准确时间/日级日期/未知日期、目标加入区间、历史补抓、旧文修改、ready 延迟、20:00 边界及匹配跨窗口延迟。时间资格和摘要去重均不可依赖测试执行当天。
7. 故障注入覆盖 R2 已写但 D1 未提交、D1 已提交但未入队、重复/乱序进展、租约过期、429/402、OCR 缺项、Auth 超时及邮件受理后响应丢失。供应商结果不明不使用第二份 payload/key 猜测恢复。
8. UI 验收覆盖真实登录、订阅创建/编辑/排序/暂停、RSS 轮换、版本阅读与受保护下载，沿用中文、双主题、响应式及现有设计规范；源码/构建通过不替代用户操作证据。
9. 本地测试、隔离 Cloudflare 实际交接、供应商实际返回、真实账号权益与生产灰度分别记录。最终真实邮箱测试仅使用明确指定的验收收件人；没有实际执行的层级标记未验证。

## Out of Scope

- 非公开或需绕过授权的来源、本机浏览器依赖、自动接入任意网站、跨 URL 的相似内容自动合并。
- 关键词/排除词订阅、一个 RSS 聚合多个订阅、站点新栏目自动加入旧订阅。
- 普通附件的通用全文 OCR、全版本全文搜索、语义推荐、用户自填任意收件地址。

## Further Notes

- 首批/中期栏目数、活跃用户数、月预算仍待定。套餐、邮件供应商最终选择、Auth 默认额度、重查细分频率、重试上限和告警阈值属于上线参数；实现必须支持配置并拒绝无界重试，不能以虚构的量级或套餐承诺验收。
- 代码行为可在可控 Adapter 和隔离配置下验证；邮件生产 Adapter 需先完成明确选型，供应商未定时 T11 不能仅凭 mock 完成而关闭。真实云端/邮件和生产切换前，须具备隔离资源、服务凭证、指定验收收件人及已确认的费用/额度配置；缺失时明确保留上线门槛，不将本地模拟写成线上通过。
- 采用 18 个纵向子任务。T01 是保持现有行为的前置整理；T02 的 Auth 可独立推进。之后依次建立单篇任务、来源管理、版本存档与完整性，再并行接入订阅/RSS、邮件和迁移，最后做隔离演练及生产灰度。
- T 编号是实现计划编号，不是 GitHub issue 编号。具体依赖由子任务的原生 blocking links 表达；ready-for-agent 表示规格可实现，不表示所有 blocker 已完成。只领取依赖已完成的 frontier；总规格不因生成子任务而关闭。
- 每个子任务从现有可工作的行为出发，包含所需数据变化、业务入口、可观察结果和验收。避免单独建立“所有数据库”“所有后端”“所有前端”横向大任务。必要跨仓库 Auth 改动由对应子任务明确管理，Feed 集中跟踪。
