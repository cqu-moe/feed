# #63 采集方案：栏目各算到期，网站错开开工

状态：#63 的验收规格。隔离演练与生产切换分开记录。[Issue #63](https://github.com/cqu-moe/feed/issues/63) 提出把单任务交给 Workflows。本次讨论修订其中的并发要求：取消跨站“同时最多两项”的业务限制，保留同站一次只抓一项。当前实现见[采集调度](../queue-collection.md)。

## 一轮采集怎样跑

1. **整点挑栏目。** 每小时的 Cron 是唯一自动扫描到期栏目的入口。每栏各算到期，只给已启用、已验证且没有在办列表任务的栏目建待办。两个栏目到期，就是两项查列表的任务。派发积压、补抓历史页不顺手再扫一遍栏目。此时不启动浏览器。
2. **给网站选时间。** 用站点 ID 和 Cron 原定的 UTC 整点算出一个 0～3599 秒的伪随机偏移，加到这个整点上。在同一轮里，同站栏目即使分批建任务，也得到同一时刻；下一轮重新计算。不需要网站排班表。只有定时首轮检查错峰；手动验证、后续翻页、新通知正文、复查、历史补抓和重试都不另外等。
3. **Queue 等，投递后才启动 Workflow。** 最早开始时间存进现有 `tasks.due_at`，待发送记录立即可派发。发送时把剩余秒数（向上取整，已过时取 0）交给单条消息的 [`delaySeconds`](https://developers.cloudflare.com/queues/configuration/javascript-apis/#queuesendoptions)。10:00 发送、计划 10:12 开始，就是 720 秒。消息在 Queue 里等，此时没有 Workflow，也不开容器。到点投递后，消费者只负责创建或确认同一任务的 Workflow，再记录已交接并确认消息。
4. **开浏览器前再看一次。** 定时列表任务轮到访问时，由 Workflow 核对站点和栏目仍启用、配置仍是任务对应的已验证版本，然后取得本站唯一的抓取名额。排队期间停用或换版，旧列表任务就取消，不抓旧网址，也不记检查成功。手动验证草稿有自己的规则。站点空闲且平台有资源时，复用或启动本站容器。同站忙或平台容量不足，在容器外等，不计抓取失败；其他站照常开工，无跨站两项上限。
5. **列表和正文分别办。** 读列表只取标题、链接和日期。有效列表没有新通知也记栏目检查成功；有符合条件的下一页就另建列表任务。每篇新通知只建一项首次正文任务，重复链接不再建。正文一旦入队就可接手，不必等下一轮整点。列表任务不等所有正文归档才结束。
6. **完成后交回结果。** 正文任务用该站的容器取得正文、应存附件和网页原貌。交回结果后，同站已有就绪任务可接着用容器；没有就请求停止。Feed 将已取回的原件和版本保存下来。需要从扫描件识字时，由独立的 OCR 任务处理。只有必需内容齐全的版本才进入订阅匹配；缺附件的版本保留缺项。

## 谁负责重试

网站临时断开或返回 429 时，同一个 Workflow 释放站点，按源站要求等待，再从已保存的列表或原件继续；实际抓取沿用现有次数上限，首次也算一次。抓取代码可能抛出异常，也可能正常返回带错误的结果，两者必须先分类，再决定是否写最终结果。永久错误、业务额度耗尽、超过上限明确记失败或阻塞。人工暂停历史补抓则等人工恢复，保留游标，不消耗抓取次数。

首次错峰归 Queue，交接后的采集和重试归 Workflow。队列消费者不预占网站、不因站忙退回待发表；站点名额只在实际抓取时取得。D1 保存任务身份、同站准入和业务结果，R2 存原件。五分钟 Cron 负责监控、补送交接失败的待办和邮件；对已经交接的浏览器任务，只核实异常终止或缺失的最终结果，不代替正常 Workflow 重试。独立 OCR 的恢复规则不随本次迁移改变。

## 10 点这一轮的例子

下列北京时间和耗时都是示意，只举一种可行的同站执行顺序。计划时间是“最早可开始”，不是平台的准点承诺。

| 时间 | 教务处 | 学工部 | 校团委 |
| --- | --- | --- | --- |
| 10:00 | 通知公告和学籍管理都到期，共用 10:12 | 一栏到期，抽到 10:13 | 一栏到期，抽到 10:14 |
| 10:12–10:15 | 查通知公告；发现一篇新通知 | 10:13 开始查列表，到 10:16 结束 | 10:14 开始查列表，到 10:16 结束 |
| 10:15–10:17 | 查学籍管理，同站一次只开一个抓取 | 有效空列表也算检查成功 | 查完后没有同站待办，容器可停 |
| 10:17 以后 | 已发现的那篇正文轮到就抓，交回正文、附件和原貌 | — | — |

10:14 到 10:15 三站同时访问，各自只做一项。移除 `feed-jobs` 原有的 `max_concurrency: 2`；实际能开的容器数仍取决于平台资源。整套排班按站点 ID 工作，不依赖不同容器一定有不同公网出口 IP。

## 切换和验收

切换时可以短暂停止领取新采集任务，继续保留积压。先让旧执行完成，或对照原记录确认其结果，再让 Workflow 接手未完成的工作。保留任务身份和已存结果，不批量重跑过去已经失败或阻塞的任务。

以下均为实施后的验收条件；以实际的入队、访问源站、归档记录为准。

启动消息的批量派发、单条补送和后台重放共用一个发送入口。对已发送、本次尝试尚未交接的消息，从计划时刻、最近发送和最近重放三者中最晚者起算现有交接宽限。后台列表和五分钟恢复扫描在分页前排除正常等待；人工重放领取消息时也复核，不能挤掉真正失联的任务。普通邮件、内容事件仍用原规则。

| 场景 | 应观察到的结果 |
| --- | --- |
| 10:00 发出，计划 10:48 开工；10:16 查后台、运行恢复扫描或点「重放」/「恢复任务」 | 不报失联、不重发、不增加补送次数。若第一次就没发出去，10:20 补送只延迟剩余 28 分钟。若旧启动消息意外提前到达，按[剩余时间退回 Queue](https://developers.cloudflare.com/queues/configuration/batching-retries/)，不记已交接。 |
| 栏目 09:01 到期，10:00 扫到，排在 10:48 | 到 10:12，来源页和监控都不误报本轮超期，也不刷新上次成功时间。只对当前这轮有有效排班的栏目计入其最早开工时刻及现有处理宽限；没排上的、上一轮漏检或已有错误仍可见。 |
| 已排班的站点在 10:20 停用，或栏目换成新版配置 | 到 10:48 不启动容器、不写成功、不新建正文。若请求已经发出才停用或换版，提交列表结果时再核对，以免旧结果发出新任务。人工验证未启用的新配置仍可运行。 |
| 同一整点扫描重入，或其间派发历史补抓 | 同站本轮各栏拿到相同计划时刻，每栏仅一项；单独派发历史页不会生成新的定时列表。三个不同站点的实际浏览器请求可重叠，同站请求不重叠；等待时不占容器。 |
| 正文返回可重试错误，或源站明确要求稍后再来 | 关闭五分钟 Cron 仍能在原 Workflow 重试；其他站继续。暂态结果不写成最终回执，到上限只记一次终态。重复投递、中断、人工恢复或切换均不重复创建首次正文、内容事件；已取回原件不重抓。 |
